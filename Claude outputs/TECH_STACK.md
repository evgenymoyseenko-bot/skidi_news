# Выбор технологий

Для каждого спорного выбора — 2-3 варианта, источник и дата. Версии проверяйте перед стартом
разработки — экосистема Python двигается быстро, приведённые версии актуальны на момент
подготовки документа (август 2026).

## 1. Веб-фреймворк: Django

**Выбор: Django 5.2 LTS**, а не Django 6.0.

| Вариант | За | Против |
|---|---|---|
| **Django 5.2 (LTS)** | Долгосрочная поддержка, стабилен, всё нужное для admin+DRF+Celery уже отработано годами | Не самый новый |
| Django 6.0 | Новее, встроенный фреймворк фоновых задач `django.tasks` | Не LTS; собственный `django.tasks`, по данным обзора, — «абстракция без реализации»: нет планировщика, повторов, персистентности «из коробки», нужен всё равно сторонний backend (django-rq/django-celery/django-apscheduler) — источник: [Django 6.0 Tasks: a framework without a worker, Loopwerk, 2026](https://www.loopwerk.io/articles/2026/django-tasks-review/) |

Вывод: раз всё равно нужен Celery для полноценного планирования (см. п.2), новый `django.tasks`
в 6.0 не даёт преимущества сейчас, а LTS даёт стабильность на годы вперёд. Источник релиза
Django 6.0: [Django 6.0 released, 3 Dec 2025, djangoproject.com](https://www.djangoproject.com/weblog/2025/dec/03/django-60-released/).

## 2. Планировщик фоновых задач: Celery + django-celery-beat

| Вариант | За | Против |
|---|---|---|
| **Celery + Redis + django-celery-beat** (Recommended) | Зрелое промышленное решение; `django-celery-beat` хранит расписание в БД и **редактируется прямо в Django admin** — то есть модератор/админ сможет менять периодичность парсинга источников без деплоя кода. Источник: [django-celery-beat 2.5.0 docs](https://django-celery-beat.readthedocs.io/en/latest/) | Больше движущихся частей (нужен Redis, отдельные процессы worker/beat) |
| Django-Q2 | Проще в установке (не нужен отдельный брокер, может работать на ORM) | Меньше экосистема, меньше готовых интеграций для наших сценариев (retries, мониторинг) |
| Django 6.0 `django.tasks` | Нативно, без доп. зависимостей на уровне абстракции | Нет планировщика/повторов «из коробки» на практике — см. п.1 |

Вывод: берём Celery — он же и для парсинга по расписанию, и для отправки в Telegram/на публикацию
с ретраями при сбоях сети.

## 3. Получение и разбор новостей

| Задача | Инструмент | Обоснование |
|---|---|---|
| Разбор RSS/Atom-фидов | **feedparser** | Стандарт де-факто для RSS в Python, простой и надёжный |
| Извлечение основного текста статьи со страницы (для источников без RSS или с урезанным summary) | **trafilatura** | По независимому бенчмарку на 990 документах (обновление 4 августа 2026) показал лучший результат: F-score 0.924, точность 0.923 — выше, чем у `newspaper4k` (F-score 0.801), `readability-lxml` (0.826), `news-please` (0.836), `goose3` (0.810, но по recall заметно хуже). Источник: [Trafilatura Evaluation, официальная документация, обновлено 4 авг. 2026](https://trafilatura.readthedocs.io/en/latest/evaluation.html) |
| HTTP-запросы к простым страницам | **requests** | Стандарт |
| Страницы с JS-рендерингом (если понадобится) | **Playwright** (уже используется в стеке, готовый Chromium под рукой) | Подключать только для источников, которые реально требуют рендеринга — не по умолчанию, т.к. дороже по ресурсам и времени |

Не тестировал совместно все три инструмента на реальных источниках проекта — перед подключением
конкретного источника проверяйте вручную, что и RSS, и HTML-парсинг дают приемлемый результат.

## 4. Дедупликация новостей

| Уровень | Механизм |
|---|---|
| Точное совпадение | `external_url` — уникальный индекс в БД, самый дешёвый и надёжный фильтр |
| Похожие новости с разных источников (разный URL, тот же текст) | **rapidfuzz** — быстрое нечёткое сравнение заголовков (и, опционально, первых N символов текста) с недавними новостями (например, за последние 3-7 дней). Источник: [RapidFuzz — rapid fuzzy string matching in Python, github.com/rapidfuzz/RapidFuzz](https://github.com/rapidfuzz/RapidFuzz) |

Порог схожести (например 85-90%) нужно будет подобрать эмпирически на реальных данных после
подключения источников — заложите это как отдельную задачу тестирования, а не константу «на глаз».

## 5. Публикация в Telegram

| Вариант | За | Против |
|---|---|---|
| **Прямой вызов Telegram Bot API** (`sendMessage`/`sendPhoto` через HTTP, можно через `aiogram.Bot` без полноценного Dispatcher) (Recommended для MVP) | Публикация — это только «отправить сообщение», постоянно работающий процесс бота не нужен; вызывается прямо из Celery-таски при одобрении новости | Если позже понадобится интерактивность (бот принимает команды модератора) — надо будет добавить процесс с polling/webhook |
| **aiogram** (полноценный бот-процесс) | Асинхронный, современный, большое русскоязычное сообщество и документация — удобно, если планируется интерактивный бот для модерации в будущем | Лишняя сущность (ещё один долгоживущий процесс), если сейчас нужна только публикация |
| python-telegram-bot | Тоже async, популярен, хорошая документация | Второй вариант в этой же нише — выбираем один, не оба; aiogram чаще встречается в RU-проектах |

Вывод: на старте используем `aiogram.Bot` только как клиент для отправки сообщений (без
Dispatcher/polling) — минимум сущностей. Если появится задача «модератор одобряет новости из
Telegram», это расширение того же клиента до полноценного бота, а не переделка архитектуры (см.
`ARCHITECTURE.md`, «Возможное развитие»).

## 5а. LLM для редактора: GigaChat

Промежуточный шаг между парсингом и модерацией — LLM-редактор отбирает и переписывает новости
по промту (`parser/EDITOR_PROMPT.md`): смысловой отбор по явно расписанным критериям + короткое
переписывание текста на русском. Задача не требует топ-уровня reasoning.

| Вариант | За | Против |
|---|---|---|
| **GigaChat (Сбер)** — выбрано | Прямая оплата в рублях, без обходных схем | Технически на физлице ограничена многопоточность (см. ниже — для нас не проблема) |
| YandexGPT (Яндекс) | Тоже прямая оплата из РФ, контекст 32K (5.1 Pro), заявлено снижение галлюцинаций | Рассматривался как равноценная альтернатива, не выбран — решение пользователя |
| OpenAI / Anthropic (GPT / Claude) | Сильнее по общей репутации в reasoning | Прямой оплаты из России нет, нужны сторонние платёжные сервисы/прокси-карты — подтверждено несколькими независимыми источниками 2026 года ([vc.ru про OpenAI](https://vc.ru/services/2966723-kak-oplatit-openai-api-iz-rossii), [vc.ru про Claude](https://vc.ru/services/2966546-kak-kupit-claude-api-iz-rossii)) — лишняя сложность и риск для маленького клубного проекта |

**Выбор пользователя: GigaChat, тариф для физического лица, модель Pro** (07.09.2026) —
осознанно на промежуточном этапе проекта, без коммерческой монетизации самого редактора.
Тарифы: freemium 40М токенов Pro-моделей/год бесплатно, платно 3М токенов/мес за 1500₽.
Источник: [тарифы GigaChat API для физлиц, developers.sber.ru](https://developers.sber.ru/docs/ru/gigachat/tariffs/individual-tariffs) (2026).

**Risk-flag (озвучен пользователю, решение принято сознательно)**: соглашение GigaChat для
физлиц ограничивает Freemium-режим «личными некоммерческими целями» и не даёт однозначного
ответа для платных тарифов физлица про использование в рамках организации. Источник:
[соглашение для физлиц, developers.sber.ru](https://developers.sber.ru/docs/ru/policies/gigachat-agreement/individuals)
(2026) — не юридическая консультация, публичная интерпретация текста. **Не поднимать этот
вопрос повторно** — пользователь принял решение сам.

**Технические ограничения (проверены, блокеров для нашего сценария нет)**:
- Физлицо: 1 поток генерации (юрлицо — 10 по умолчанию). Наш паттерн — один последовательный
  запрос на батч, 2 раза в день, конкурентность не нужна. Источник:
  [developers.sber.ru/docs/ru/gigachat/limitations](https://developers.sber.ru/docs/ru/gigachat/limitations) (2026).
- Контекст: GigaChat-Pro — 32K токенов, GigaChat-2-Pro — 128K, оба доступны на тарифе физлица —
  с запасом хватает на батч из нескольких десятков коротких новостей.

**Работа кодера (не блокирует, но нужно решить при реализации)**: конкретный SDK/HTTP-клиент
для вызова GigaChat API, где и как хранить ключ/секрет (переменная окружения, см.
`.env.example`), формат передачи батча (прямой вызов из Celery-таски / файл / очередь),
разделитель между постами в текстовом ответе редактора и способ передать факт отсутствия
картинки у конкретной новости.

## 5б. Email-инфраструктура для модерации

Модерация новостей идёт через письма на `info@skidiscoverer.ru` с подписанными ссылками
(`django.core.signing`, без отдельной таблицы токенов — механизм подробно описан в
`docs/DATA_MODEL.md`, раздел «Модерация по email и очередь публикации»). Для этого нужен
рабочий email backend в Django (`EMAIL_BACKEND` + SMTP-настройки, или сервис вроде
django-anymail под конкретного провайдера).

**Открытый вопрос (не решён, требует владельца проекта)**: кто хостит `info@skidiscoverer.ru`
и какой там SMTP/провайдер — не обсуждалось и не исследовалось. Без этого нельзя окончательно
выбрать между обычным Django `SMTPEmailBackend` и `django-anymail` (нужен, если провайдер
предпочитает работу через собственный API, а не SMTP). Уточнить у Бро перед этапом 3 в
`docs/CODER_INSTRUCTIONS.md`.

## 6. API для интеграции с ЛК

**Django REST Framework (DRF)** — стандартный, самый распространённый инструмент для REST API
поверх Django, глубоко интегрирован с моделями и admin. Альтернатив с существенными
преимуществами для этой простой задачи (отдать список новостей по HTTP) нет смысла
рассматривать — это общепринятый выбор для Django-проектов.

## 7. Видеохостинг для базы знаний

Видео-примеры техники катания — платный контент для участников клуба. Своё хранилище видео мы
не поднимаем: транскодирование под разные устройства/скорости, защита от скачивания и
адаптивный стриминг — отдельная дорогая инженерная задача, которую готовые видеохостинги уже
решили.

| Вариант | За | Против |
|---|---|---|
| **Kinescope** (Recommended) | Позиционируется прямо для онлайн-школ: DRM-шифрование, динамические водяные знаки, ограничение доступа по доменам, интеграция с LMS, кастомизация плеера, аналитика просмотров. Источник: [Kinescope vs VK Видео — сравнение, kinescope.ru/blog](https://kinescope.ru/blog/kinescope-vs-vk-video-kakuyu-platformu-vybrat) | Платный сервис (конкретные тарифы уточнить на сайте — не проверял на момент написания) |
| VK Видео | Бесплатнее/проще подключить | По тому же источнику — заточен под соцмонетизацию, нет LMS-интеграции и полноценного управления доступом подписчиков, то есть для «платных уроков» подходит хуже |
| Самостоятельный хостинг (S3 + транскодирование + HLS) | Полный контроль | Ощутимо дороже в разработке и поддержке для небольшой команды; своя защита от скачивания придётся писать с нуля |

Вывод: подключаем Kinescope. Наша БД хранит только `video_provider` + `video_id`/embed-код
(см. `docs/KNOWLEDGE_BASE.md`) — сами видеофайлы никогда не проходят через наш бэкенд.

**Не проверено**: конкретный механизм, которым Kinescope ограничивает просмотр по подписке
конкретного участника (доменные ограничения vs подписанные временные токены) — уточнить в
документации Kinescope при реализации `knowledge_base`, это может повлиять на то, как ЛК
встраивает плеер.

## 8. Файловое хранилище для документов базы знаний

Помимо видео, в базе знаний могут быть документы (PDF-методички и т.п., не видео).

| Вариант | За | Против |
|---|---|---|
| Локальный диск контейнера / volume | Проще всего на старте, ничего доп. подключать не нужно | Не годится при масштабировании на несколько инстансов `web`; при пересборке контейнера без правильного volume можно потерять файлы |
| **S3-совместимое объектное хранилище** через `django-storages` (Recommended) | Готовое решение, стандарт для Django; можно использовать любой S3-совместимый провайдер (Yandex Object Storage, Selectel, MinIO для локальной разработки) — не привязывает к конкретному облаку | Требует завести бакет и ключи доступа перед продакшен-запуском |

Вывод: для локальной разработки — volume/локальный диск, для продакшена — `django-storages` +
S3-совместимое хранилище. Выбор конкретного провайдера — на усмотрение Бро (зависит от того,
где уже есть инфраструктура для skidiscoverer), сам код на это не завязан.

## 9. Чат-бот участников: информационное меню без ИИ

Договорились, что чат-бот — не ИИ-ассистент и не собирает заявки, а только показывает меню со
ссылками (новости, база знаний, ссылка на форму консультации, «о клубе»). Реализуется на
**aiogram** (та же библиотека, что уже выбрана для публикации новостей в Telegram, см. п.5) —
обработчиков команд и callback-кнопок инлайн-клавиатуры достаточно для плоского меню. Модуль
`aiogram.fsm` (конечный автомат состояний) для этого не обязателен — он нужен там, где бот
собирает данные в несколько шагов или помнит глубокую навигацию по вложенным меню; раз бот
сейчас ничего не собирает, закладывать FSM заранее — это сложность ради сложности. Источники по
FSM оставляю на случай, если сценарии бота позже усложнятся: [Telegram Боты на Aiogram 3.x: Все
про FSM — Habr, 2024](https://habr.com/ru/articles/822061/), [официальный гайд по FSM для
aiogram 3.x](https://mastergroosha.github.io/aiogram-3-guide/fsm/).

Отдельная ИИ-библиотека/LLM-интеграция не нужна — сознательно не закладываем в стек, чтобы не
усложнять то, что должно остаться простым. Подробности сценариев — `docs/CHATBOT.md`.
