# CLAUDE.md — для Claude Code

Этот файл — точка входа для Claude Code при работе в этом репозитории. Он не дублирует
документацию, а указывает, что читать и в каком порядке, и фиксирует несколько правил, которые
легко нарушить, не зная историю решений.

## Что это за проект

Бэкенд экосистемы **skidiscoverer** (лендинг на Тильде + Telegram-канал новостей + Telegram-чат
участников + Личный кабинет с базой знаний по горнолыжной технике). Один Django-проект,
несколько apps: `news` (парсинг → LLM-редактор → email-модерация → публикация), `knowledge_base`,
`consultations`, `chatbot`. Полная картина — `README.md` в корне.

## С чего начать

1. `README.md` — обзор проекта, карта документов, актуальный список открытых вопросов.
2. `docs/ARCHITECTURE.md` — компоненты, поток данных (mermaid), жизненный цикл новости.
3. `docs/TECH_STACK.md` — выбор технологий с обоснованием и источниками (включая LLM-редактор).
4. `docs/DATA_MODEL.md` — модели `news`, включая раздел «Модерация по email и очередь
   публикации» — это ядро логики модерации/публикации, читать внимательно перед реализацией
   этапов 3-5 из `docs/CODER_INSTRUCTIONS.md`.
5. `docs/CODER_INSTRUCTIONS.md` — пошаговый план сборки, главный рабочий документ. Идти по нему
   последовательно.

## Критичные ограничения — не нарушать

- **`parser/` — рабочая эталонная реализация, не черновик.** 20/20 тестов проходят
  (`cd parser && python3 -m unittest discover -s tests -v`). Логика парсинга/дедупа-фильтров
  переносится в Django-app `news` максимально близко к этому коду. Если меняешь эту логику при
  переносе — тесты перенести и адаптировать вместе с ней, не терять покрытие.
- **Модерация новостей — НЕ через Django admin.** Это единственная область, где `news`
  осознанно отличается от `consultations` (там модерация обычная, через admin). Не «упрощай»
  обратно в admin-actions — email-ссылки с подписанными токенами (`django.core.signing`) это
  осознанное решение, см. `docs/DATA_MODEL.md`.
- **Картинка у новости необязательна.** Решение от 07.09.2026 отменяет более раннее «картинка
  обязательна». Публикуем и с `image_url`, и без (`sendPhoto` vs `sendMessage` в Telegram).
- **LLM-редактор — GigaChat, тариф для физлица, уровень Pro.** Решение финальное
  (`docs/TECH_STACK.md`, п.5а). Не предлагать альтернативы (YandexGPT, OpenAI/Anthropic) заново —
  сравнение уже сделано, вопрос закрыт владельцем продукта.
- **Очередь публикации — без верхнего лимита.** Растёт естественно, publish — фиксировано 2
  записи за прогон (4/день), срочные первыми. Не добавлять cap/eviction — раньше была идея с
  cap=8 и статусом `expired_unpublished`, от неё отказались в пользу еженедельной re-модерации.

## Что помечено «работа кодера» — решать самостоятельно, не спрашивать владельца продукта

В `docs/CODER_INSTRUCTIONS.md` и `docs/TECH_STACK.md` отдельные пункты явно помечены как
делегированные кодеру: способ хранения ключа GigaChat, конкретный SDK/HTTP-клиент, транспорт
батча между этапами пайплайна внутри проекта, сигнализация «нет картинки» в тексте поста от
редактора, выбор email-библиотеки поверх Django `EMAIL_BACKEND`. Эти решения не требуют
согласования — предложи оптимальный вариант и реализуй.
