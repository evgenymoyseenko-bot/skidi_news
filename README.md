# Бэкенд экосистемы skidiscoverer — обзор проекта

Единый вспомогательный бэкенд для проекта **skidiscoverer** (лендинг на Тильде + ТГ-канал
новостей + ТГ-чат участников + Личный кабинет с базой знаний по технике катания на горных
лыжах). Это не «парсер новостей отдельно» — это один Django-проект с несколькими модулями
(apps), из которых парсер новостей — только один:

- **news** — сбор новостей из внешних источников → дедупликация → модерация → публикация в
  Telegram-канал и в ЛК.
- **knowledge_base** — материалы по технике катания (видео + документы), которые ЛК
  показывает участникам.
- **consultations** — заявки на консультацию с формы на Тильде → уведомление менеджеру +
  карточка в Django admin. Не связан с `chatbot` — разные формы для разных целей.
- **chatbot** — простой информационный Telegram-бот без ИИ (меню/кнопки/ссылки) для участников
  клуба: новости, база знаний, ссылка на форму консультации. Заявок сам не собирает.

Это пакет **архитектуры и инструкций** для разработчика (кодера-сборщика). Кода приложения
здесь нет намеренно — есть модели, контракты API, схема БД и пошаговый план сборки. Задача
разработчика — реализовать по этим документам.

## Контекст проекта

- Экосистема skidiscoverer сейчас: лендинг на Тильде + Telegram-канал новостей + Telegram-чат
  участников клуба + **Личный кабинет участника клуба** (ЛК) с базой знаний по технике катания
  на горных лыжах (видео-примеры). ЛК — отдельный проект (`skidiscoverer/lk`), стек
  зафиксирован (Tilda + Supabase). **12.09.2026: интеграция новостей с ЛК реализована** — push
  в `publish-news` (Supabase Edge Function) при каждой публикации, см.
  `docs/LK_INTEGRATION_TASK.md`, подтверждено реальными новостями в карусели на
  `skidiscoverer.ru/lk`.
- Этот бэкенд — отдельный от ЛК сервис (Python/Django), который не встроен в ЛК напрямую, а
  отдаёт данные через push при публикации (см. `docs/LK_INTEGRATION_TASK.md` —
  `docs/INTEGRATION_LK.md` устарел, описывал другой, нереализованный контракт). Осознанное
  решение:
  два проекта разрабатываются параллельно и не должны блокировать друг друга по срокам и
  стеку — при этом сам бэкенд не дробится на несколько сервисов ради этих 4 модулей, они живут
  в одном Django-проекте как отдельные apps (см. `docs/ARCHITECTURE.md`, раздел «Почему один
  проект, а не четыре сервиса»).
- Модерация заявок на консультацию — через Django admin (обычная админка Django, без
  кастомной панели, без внешней CRM). Модерация новостей устроена иначе (уточнено 07.09.2026,
  отменяет более раннюю идею admin-модерации новостей) — через email со ссылками-действиями
  (без логина, без отдельной панели, без отдельной таблицы токенов), подробности —
  `docs/DATA_MODEL.md`, раздел «Модерация по email и очередь публикации», и
  `docs/ARCHITECTURE.md`, п.9.
- Перед модерацией новости проходят через LLM-редактора (GigaChat, тариф для физлица, уровень
  Pro — обоснование и сравнение вариантов в `docs/TECH_STACK.md`, п.5а) — отбирает подходящие
  из батча и переписывает в готовый пост. Промт — `parser/EDITOR_PROMPT.md`.
- Публикация новостей — в Telegram-канал и в блок новостей ЛК, по 2 записи из очереди на каждый
  из двух запусков в день (4/день), без верхнего лимита на размер самой очереди — подробности
  там же, в `docs/DATA_MODEL.md`.
- Чат-бот — без ИИ, чисто информационное меню на кнопках (aiogram); заявок не собирает и не
  связан с формой консультации, кроме статической ссылки на неё.
- База знаний — материалы без полнотекстового поиска, видео — через внешний видеохостинг
  (не храним видеофайлы сами, см. `docs/TECH_STACK.md`).
- Список источников новостей ещё не утверждён — см. `docs/SOURCES.md` с методологией
  подбора и кандидатами на проверку.

## С чего начать разработчику

1. Прочитать `docs/ARCHITECTURE.md` — понять общую картину и структуру модулей.
2. Прочитать `docs/TECH_STACK.md` — понять, почему выбраны именно эти инструменты.
3. Идти по чек-листу в `docs/CODER_INSTRUCTIONS.md` — там пошаговый план с ссылками на
   остальные документы в нужный момент.

## Открытые вопросы (нужно решить до/во время разработки)

**Уже решено, переоткрывать не нужно:** LLM для редактора — GigaChat, тариф для физлица,
уровень Pro (сравнение и технические лимиты — `docs/TECH_STACK.md`, п.5а); правило по картинке —
необязательна, публикуем и с ней, и без (`parser/README.md`); очередь публикации — без верхнего
лимита, 2 записи за прогон (`docs/DATA_MODEL.md`); провайдер писем для email-модерации —
UniSender Go через `django-anymail` (07.09.2026, см. `docs/TECH_STACK.md`, п.5б); квота
редактора 6/день делится 3/3 на батч (07.09.2026, см. `docs/DATA_MODEL.md`); разделитель между
постами в ответе редактора и связка пост↔картинка (07.09.2026, см. `parser/EDITOR_PROMPT.md`).
Часть вопросов реализации (детали вызова GigaChat, хранение ключа, транспорт батча внутри
проекта, формат поста при отсутствии картинки) переданы кодеру как «работа кодера» — не требуют
отдельного согласования с владельцем продукта, см. пометки в `docs/CODER_INSTRUCTIONS.md`.

**07-09.09.2026**: Этапы 0-5 из `docs/CODER_INSTRUCTIONS.md` (парсинг → LLM-редактор →
email-модерация → очередь публикации → Telegram) реализованы в этом репозитории — код в корне
(`manage.py`, `config/`, `sources/`, `news/`), рядом с `parser/`, 64 автотеста. Частично
проверено реальными сервисами (не только моками): 11 из 32 источников подключены и парсятся
вживую (`docs/SOURCES.md`), GigaChat-редактор и UniSender Go отправка письма проверены реальными
вызовами (09.09.2026). **Не проверено вживую**: клик по ссылке модерации (нужен публичный
`SITE_BASE_URL`), реальная публикация в Telegram (нужен bot token). Сервер под это не арендован
— требования описаны в `docs/DEPLOYMENT.md`, «Требования к серверу». Точный статус по каждому
пункту — `docs/CODER_INSTRUCTIONS.md`, «Определение готовности MVP». Этапы 6-11 (API для ЛК,
`knowledge_base`, `consultations`, `chatbot`-меню) пока не входят в реализацию.

Ниже — то, что реально требует решения:

- Финальный список источников новостей (владелец: Бро, см. `docs/SOURCES.md` — 11/32 уже
  подключены, приоритет был на курортах и Кубке мира).
- Стек ЛК участника клуба — как только определится, проверить контракты API в
  `docs/INTEGRATION_LK.md` на совместимость (сами контракты REST/JSON универсальны и не
  зависят от стека ЛК, но URL/аутентификацию нужно будет согласовать). Отдельная нерешённая
  идея — публиковать новости в ЛК зеркалированием уже опубликованного из Telegram-канала вместо
  отдельного pull/push API (см. `docs/ARCHITECTURE.md`, п.8, и `docs/CODER_INSTRUCTIONS.md`,
  этап 7) — не реализовывать без отдельного запроса.
- Точный механизм отправки формы с Тильды на наш `/api/v1/consultations/` — у Тильды
  ограниченные возможности кастомизации вебхука (см. `docs/CONSULTATIONS.md`, «Открытый
  вопрос»), нужно проверить на реальном лендинге. Это вопрос модуля `consultations`, к парсингу
  новостей отношения не имеет.
- Как именно Kinescope (или выбранная альтернатива) будет ограничивать доступ к видео по
  подписке участника — нужно сверить с документацией провайдера при реализации (см.
  `docs/TECH_STACK.md`, «Видеохостинг»). Это вопрос модуля `knowledge_base`, к парсингу новостей
  отношения не имеет.
- Формат еженедельного обзора уже опубликованных новостей (если вообще понадобится) — пока не
  решено, описано как открытая идея в `docs/DATA_MODEL.md`.
- Нужен ли модератору интерактивный Telegram-бот вместо email-ссылок для одобрения новостей
  прямо из чата — в MVP не входит, архитектура оставляет для этого место как альтернативный
  канал модерации (см. `docs/ARCHITECTURE.md`, «Возможное развитие»).
