# Инструкция для разработчика: план сборки

Читать в связке с `ARCHITECTURE.md` (общая картина, структура apps, диаграмма потока),
`DATA_MODEL.md` (модели `news`, включая раздел «Модерация по email и очередь публикации» —
это ключевой раздел для этапов 3-5 ниже), `KNOWLEDGE_BASE.md`, `CONSULTATIONS.md`, `CHATBOT.md`
(модели и сценарии остальных модулей), `TECH_STACK.md` (почему именно эти инструменты, включая
выбор GigaChat), `INTEGRATION_LK.md` (контракт API), `DEPLOYMENT.md` (инфраструктура),
`SOURCES.md` (список источников и что нужно проверить перед подключением). Этапы 0-8 — модуль
`news` (можно реализовать и сдать первым, он не зависит от остальных трёх модулей). Этапы 9-11 —
остальные модули, их порядок между собой не принципиален.

**Есть работающий референс-скелет парсинга**: `parser/` в корне репозитория — standalone-код
(без Django), уже покрытый тестами (`python3 -m unittest discover -s parser/tests -v`, 20/20
зелёных), реализующий и проверяющий на реальных данных (фикстура RSS ТАСС) детерминированные
правила фильтрации: категория «обучение» исключена, не старше 30 дней (запись без даты тоже
считается устаревшей), картинка необязательна (если нашлась — берём, если нет — `image_url=None`,
запись всё равно идёт в батч). Порт этой логики в Django-модель `news` на этапе 2 — а не
переписывание с нуля. `parser/EDITOR_PROMPT.md` — финальный промт LLM-редактора, тоже готов к
использованию как есть.

Код Django-приложения (модели, views, celery-таски) в этом пакете не поставляется намеренно —
ниже описано **что** реализовать на каждом шаге, конкретная реализация (структура файлов,
имена переменных и т.п.) — на усмотрение разработчика, если не противоречит моделям и
контрактам из документов. Пункты, явно помеченные **«работа кодера»** — решения, которые
пользователь (владелец продукта) сознательно делегировал: не нужно с ним их согласовывать,
нужно просто выбрать разумный вариант и, желательно, коротко задокументировать выбор.

## Этап 2. Парсинг

- Реализовать парсер для `source_type = rss` на `feedparser` — портировать логику из
  `parser/sources.py` (уже написана и покрыта тестами): `canonicalize_url()`, извлечение
  картинки best-effort (`media:content` / `content:encoded` / `<img>` в summary /
  `<enclosure type="image/...">`), очистка HTML из title/text.
- Реализовать парсер для `source_type = html` на `requests` + `trafilatura` (селекторы — из
  `Source.parser_config`) — это НЕ покрыто в `parser/`, писать с нуля по контракту `NewsItem`.
- Детерминированные правила фильтрации (отбрасывают запись до сохранения в БД):
  - категория «обучение» и родственные — исключить (см. `EXCLUDED_CATEGORY_SUBSTRINGS` в
    `parser/sources.py`);
  - не старше `MAX_ARTICLE_AGE_DAYS = 30` дней, запись без даты тоже считается устаревшей;
  - **картинка НЕ фильтрует** — если есть, сохранить в `image_url`, если нет — оставить пустым,
    запись всё равно сохраняется. Это изменилось 07.09.2026 (раньше картинка была обязательной)
    — если увидите в старых заметках/коде обратное, ориентируйтесь на этот документ.
- Нормализация результата в общий формат перед сохранением в `Article` (единые поля title/
  url/content/date независимо от типа источника).
- Дедупликация по `external_url` (unique constraint на уровне БД — самый дешёвый первый
  фильтр) + rapidfuzz-сравнение заголовков с недавними новостями для случая «разные источники,
  один и тот же инфоповод» (см. `TECH_STACK.md`, п.4).
- Celery-таска парсинга запускается по расписанию **06:00 и 18:00 UTC** (два фиксированных
  времени, не интервал) — синхронно с остальными задачами ветки `news` (LLM-редактор,
  публикация), см. `django-celery-beat`.
- Проверка готовности: ручной запуск таски на 1-2 тестовых источниках даёт новые `Article`
  (картинка есть или нет — неважно), повторный запуск не создаёт дублей.

## Этап 3. LLM-редактор (GigaChat)

Новый этап, специфичный для этой ветки архитектуры — раньше в этом документе не было.

- После парсинга (и до email-модерации) свежесобранный батч `Article` со `status`, ещё не
  прошедшим редактора, отправляется в GigaChat вместе с промтом из `parser/EDITOR_PROMPT.md` и
  контекстом «недавно опубликованное» (для смыслового дедупа — глубина/формат истории **работа
  кодера**, разумная отправная точка — заголовки опубликованного за последние 3-7 дней).
- **Работа кодера**: конкретный SDK/HTTP-клиент для вызова GigaChat API, хранение ключа/секрета
  в `.env`, формат передачи батча (прямой вызов из Celery-таски — самый простой вариант при
  нашем объёме, 2 раза в день). Технически обоснование выбора GigaChat — `TECH_STACK.md`,
  раздел 5а (там же — проверенные лимиты: 1 поток на физлице, контекст 32-128K, обоим с запасом
  хватает на наш крошечный батч).
- Промт возвращает **текст** (не JSON, подтверждено пользователем) — список готовых постов.
  **Работа кодера**: разделитель между постами в текстовом ответе + способ понять, к какому
  посту какая картинка (или её отсутствие) относится — в промте это явно не формализовано,
  нужно либо расширить промт (согласовав формулировку с существующим текстом в
  `EDITOR_PROMPT.md`), либо решить на уровне парсинга ответа (например, сопоставление по
  порядку/заголовку). Задокументировать выбранный подход в `EDITOR_PROMPT.md` или рядом.
- Для каждой новости, которую редактор одобрил: `editor_verdict='publish'`, заполнить
  `edited_title`, `edited_post_text` (уже в формате поста — заголовок, 2-4 предложения,
  хэштеги, строка «Источник: <ссылка>»), `editor_processed_at`, перевести `status` →
  `pending_moderation`. Для отклонённых редактором — `editor_verdict='reject'`, дальше не идёт.
- Проверка готовности: прогон реального батча через GigaChat даёт осмысленный текстовый ответ,
  который разбирается на отдельные посты без потери новостей и без путаницы, к какой новости
  какая картинка относится.

## Этап 4. Email-модерация

Заменяет более раннюю версию этого документа, где модерация шла через admin-actions —
пользователь явно попросил модерацию по email-ссылкам, см. `DATA_MODEL.md`.

- Как только `Article.status` становится `pending_moderation` — сразу (не батчем, по мере
  обработки редактором) отправить **одно письмо на одну новость** на `info@skidiscoverer.ru`.
  Тело письма: `edited_title`, `edited_post_text` целиком (уже включает ссылку на источник),
  картинка (если есть), три ссылки-действия: «Опубликовать» / «Опубликовать срочно» /
  «Отклонить». После отправки — `moderation_email_sent_at = now()` (защита от повторной
  отправки: таска-рассыльщик берёт `status='pending_moderation' AND
  moderation_email_sent_at IS NULL`).
- **Работа кодера**: провайдер/SMTP для `info@skidiscoverer.ru` не определён (открытый вопрос,
  см. `TECH_STACK.md` раздел 5б) — уточнить у владельца проекта перед этим этапом, от этого
  зависит выбор `EMAIL_BACKEND` (обычный SMTP vs `django-anymail`).
- Ссылки — подписанные токены через `django.core.signing`
  (`dumps({"article_id": ..., "action": "publish"|"publish_urgent"|"reject"})`,
  `TimestampSigner`, разумный `max_age`, например 30 дней). Без отдельной таблицы токенов.
  Django-view по клику: сначала проверяет текущий `status`/`published_at` статьи — если уже не
  `pending_moderation`/`approved` соответственно (кто-то кликнул раньше, письмо переслали,
  и т.п.) — показывает «уже обработано», ничего не меняет повторно. Клик не требует логина в
  Django — сама подпись и есть авторизация. «Опубликовать срочно» ставит `is_urgent=True`.
- **Очередь публикации** — не отдельная таблица, вычисляемая выборка:
  `Article.objects.filter(status='approved', published_at__isnull=True).order_by('-is_urgent', 'source_published_at')`.
  **Без верхнего лимита** — если предложение превышает дневной спрос, лишнее просто ждёт своей
  очереди, ничего не удаляется и не «протухает» автоматически.
- **Еженедельная re-модерация**: по понедельникам в 06:00 UTC — Celery-таска берёт все
  `Article(status='approved', published_at__isnull=True)` и отправляет **одно письмо-дайджест**
  (не пачку отдельных писем) со списком заголовков, у каждой строки — те же три ссылки-действия
  (тот же механизм токенов, применяется повторно к уже `approved` записи). Цель — не дать
  устаревшим новостям опубликоваться без свежей проверки. После отправки —
  `last_requeue_email_sent_at = now()` на каждой включённой записи (для аудита).
- **Напоминание о нехватке**: если на момент публикации (см. этап 5) одобренных-неопубликованных
  записей в очереди меньше 4 — письмо-напоминание на `info@skidiscoverer.ru`, что можно
  опубликовать что-то своё вручную в Telegram. **Работа кодера**: проверять это один раз в день
  (на прогоне 06:00 UTC), не на обоих, чтобы не дублировать напоминание за один день.
- Проверка готовности: письмо реально приходит на `info@skidiscoverer.ru` сразу после того, как
  редактор одобрил новость; клик по каждой из трёх ссылок меняет `status`/`is_urgent` корректно
  и один раз; повторный клик по уже использованной ссылке ничего не ломает; дайджест по
  понедельникам приходит и содержит только реально зависшие записи.

## Этап 5. Очередь публикации и отправка в Telegram

Заменяет более раннюю версию «Этап 4. Публикация» — теперь публикация идёт из очереди по
фиксированному темпу, а не сразу по клику модератора.

- Celery-таска публикации запускается **дважды в день, 06:00 и 18:00 UTC** (те же времена, что
  и парсинг) — на каждом прогоне берёт **первые 2 записи** из очереди (запрос из этапа 4),
  публикует их (через активные `PublishChannel`, на старте — только `telegram`), переводит
  `status` → `published`, `published_at = now()`. Итог — **4 публикации в день**.
  - `telegram`: вызов Telegram Bot API (`aiogram.Bot` как клиент, без Dispatcher — см.
    `TECH_STACK.md`, п.5) — **`sendPhoto` с подписью, если у новости есть `image_url`, иначе
    `sendMessage`** (картинка необязательна, см. этап 2). Сохранить `telegram_message_id`.
  - **Строка «Источник: <ссылка>» перед отправкой в Telegram заменяется на «Источник:
    <название Source>» обычным текстом, без ссылки и без markdown-разметки** (решено
    09.09.2026, владелец канала: антиспам-бот канала удаляет посты со ссылками и блокирует
    источник, недопустима любая кликабельность). Ссылка остаётся рабочей только в
    `edited_post_text` (БД) и в письме модератору (`news/moderation/emails.py`) — для сверки с
    оригиналом. Подробности — `parser/EDITOR_PROMPT.md`, раздел «Решено 09.09.2026». Следствие:
    `Source.name` должен быть коротким и подходящим для публичного отображения в посте, не
    рабочей меткой для админки.
  - Запись результата (успех/ошибка) в `PublicationLog` для каждого канала и попытки.
- Ретраи при сетевых ошибках — экспоненциальный backoff (Celery `autoretry_for`, 3 попытки).
- Проверка готовности: одобренная новость реально появляется в тестовом Telegram-канале (с
  картинкой или без — в зависимости от исходной новости), при временной недоступности API
  Telegram таска повторяется, а не падает молча; за день публикуется ровно 4 новости, если в
  очереди достаточно материала.

## Этап 7. (Опционально, после этапа 6) Доставка новостей в ЛК

- Есть два варианта, оба не обязательны для MVP:

  - **Зеркалирование из Telegram** (идея пользователя от 07.09.2026, не решение) — вместо
    отдельного API-вызова из `news`, публиковать в ЛК то, что уже ушло в Telegram-канал. Не
    проектировать и не реализовывать без отдельного явного запроса владельца проекта — просто
    имейте в виду как более простую альтернативу, если её попросят.
- Не блокирует MVP — pull-API из этапа 6 самодостаточен.

## Этап 8. Источники (заполнение данными, не код)

- После утверждения списка (см. `SOURCES.md`) — добавить источники через admin, для каждого

## Определение готовности MVP

Статус на 09.09.2026 — код по всем пунктам ниже реализован и покрыт тестами (64 автотеста), но
это ≠ проверено на реальной инфраструктуре целиком. Отмечено там, где уже проверено реальными
сервисами (не моками), чтобы не путать «код готов» с «проверено вживую».

- Источники опрашиваются по расписанию (06:00/18:00 UTC) без ручного вмешательства. Расписание
  сидируется командой `setup_periodic_tasks` — **не проверялось автоматическим запуском** (нет
  поднятого `worker`/`beat` на сервере), только ручным вызовом таски.
- Дубликаты не долетают до LLM-редактора в заметном количестве (порог rapidfuzz подобран на
  реальных данных, а не оставлен «по умолчанию»). **Порог (87%) — дефолт, не подобран
  эмпирически** — пока не наблюдалось достаточно реальных дублей для калибровки.
- LLM-редактор (GigaChat) отбирает и переписывает новости в готовые посты по промту. **Проверено
  реальным вызовом 09.09.2026** на батче из 26 живых новостей — 6 одобрено, формат/разделитель
  соблюдены. По пути нашлась и исправлена ошибка (полный текст статьи не долетал до редактора,
  см. `TECH_STACK.md` п.5а и `parser/EDITOR_PROMPT.md`).
- Модератор получает письмо на `info@skidiscoverer.ru` на каждую одобренную редактором новость
  и может опубликовать/пометить срочной/отклонить одним кликом по ссылке. **Отправка письма
  проверена реально** (UniSender Go, 09.09.2026, дошло с задержкой ~минута). **Клик по ссылке —
  не проверен** (нужен публичный `SITE_BASE_URL`, сейчас `localhost`/заглушка — см.
  `DEPLOYMENT.md`, «Требования к серверу»).
- Очередь публикации без лимита корректно сортирует срочные первыми, остальные — по дате
  источника; публикуется ровно 2 записи на каждый из двух ежедневных прогонов.
- Еженедельный дайджест re-модерации (пн 06:00 UTC) уходит и содержит только реально зависшие
  записи; при нехватке материала (< 4 в очереди) модератору приходит напоминание.
- Одобренная новость публикуется в Telegram-канал — с картинкой, если она была у источника, без
  неё — если не было. **Не проверено реальной отправкой** — нет `TELEGRAM_BOT_TOKEN`/тестового
  канала. Текст перед публикацией заменяет ссылку на источник его названием (без ссылки, см.
  `parser/EDITOR_PROMPT.md`, «Решено 09.09.2026») — требование владельца канала, антиспам-бот
  блокирует посты со ссылками.
- ЛК (или тестовый клиент, имитирующий ЛК) может получить список опубликованных новостей через
  `GET /api/v1/news/` с токеном.
- Ошибки парсинга/GigaChat/email/публикации видны в admin/логах, а не теряются молча.
- ЛК может получить каталог базы знаний через `GET /api/v1/knowledge-base/materials/`.
- Заявка с формы Тильды (`POST /api/v1/consultations/`) доходит до admin и до уведомления
  менеджеру.
- Информационное меню бота работает и нигде не пытается писать в `ConsultationRequest`.
