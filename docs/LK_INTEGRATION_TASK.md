## Расхождение с `docs/INTEGRATION_LK.md` — явно, по правилу 7 из корневого CLAUDE.md

`INTEGRATION_LK.md` в этом же репозитории описывает **другой** контракт: универсальный
pull-REST-API (`GET /api/v1/news/`) + опциональный push-вебхук, написанный на момент, когда
«стек ЛК ещё не зафиксирован». Стек ЛК давно зафиксирован (Tilda + Supabase, см.
`skidiscoverer/lk/README.md`) — и что важнее, **на стороне ЛК уже готова своя точка приёма
именно под эту интеграцию**: Edge Function `publish-news` + таблица `news` + секрет
`LK_NEWS_TOKEN` (см. `skidiscoverer/lk/backend/edge-functions/publish-news/index.ts`,
`skidiscoverer/lk/docs/api-contract.md`, `skidiscoverer/lk/docs/open-questions.md` п.11).

Использовать **эту готовую точку** (push от парсера в `publish-news`), а не строить
отдельный REST API по `INTEGRATION_LK.md` — meньше кода, не дублирует то, что уже
спроектировано и частично реализовано на стороне ЛК. `INTEGRATION_LK.md` считать устаревшим
черновиком, актуальную схему см. ниже.

## Что уже готово на стороне ЛК (проверено чтением кода 12.09.2026)

- Таблица `news` (`lk/backend/schema.sql`): `id`, `title`, `body`, `is_urgent`,
  `published_at`, плюс `category` (`check` на `club|world_cup|resort_cis|resort_asia|
  resort_europe|resort_americas`), `source_name`, `source_url`. RLS **не включён** —
  таблица читается анонимным (`publishable`) ключом напрямую с клиента, без токена.
- `publish-news` (`lk/backend/edge-functions/publish-news/index.ts`) — принимает
  `POST {title, body, is_urgent}` с `Authorization: Bearer <LK_NEWS_TOKEN>`, пишет в `news`.
  **Сейчас НЕ принимает `category`/`source_name`/`source_url`** — колонки в таблице есть, в
  коде функции нет. Нужно расширить (см. «Задача 2» ниже).
- `LK_NEWS_TOKEN` — отдельный секрет только для этой функции (не общий `LK_ADMIN_TOKEN`),
  заведён специально, чтобы парсеру не давать лишние права. **Не проверено, установлен ли
  он реально** в Supabase secrets — свериться с Бро/кодером ЛК перед стартом (команда:
  `supabase secrets set LK_NEWS_TOKEN=<значение>`, сгенерировать через `openssl rand -hex 32`,
  если ещё не сделано).
- Все Edge Functions проекта задеплоены с флагом `--use-api --no-verify-jwt` — без него
  Supabase отклоняет запрос как 401 ещё до кода функции (`lk/docs/deploy-2026-08-21.md`).
  Учитывать при редеплое `publish-news`.
- `lk-common.js` уже имеет готовый generic-хелпер `readPublic(table, query)` — публичное
  чтение через PostgREST анонимным ключом, без Bearer. Для новостей на клиенте не нужно
  писать новый способ запроса, только вызвать `readPublic('news', 'order=published_at.desc&limit=1')`.
- Блок «Новости клуба» на `/lk` (`lk/pages/lk-home.html`, секция `.ski-news`) — сейчас
  статичная заглушка-параграф (`#ski-news-list`). Решение по вёрстке уже принято 30.08.2026:
  **показывать ОДНУ (последнюю) новость**, не список — компактная карточка в духе мобильного
  приложения. CSS-классы уже подготовлены: `.ski-news-item`, `.ski-news-item--urgent`
  (жирный/акцентный цвет для срочных).
- **Известный риск, зафиксирован в `lk/docs/open-questions.md` (адверсериальное ревью,
  ~строка 486): XSS через `innerHTML` в блоке новостей**, если/когда его реализуют наивно.
  Заголовок/текст новости — external input (в конечном счёте из текста с сайтов-источников,
  прошедшего через GigaChat) — при рендере **обязательно** `textContent`, не `innerHTML`.
- 152-ФЗ блокировка (`open-questions.md`, п.12) **не касается этой интеграции** — она
  запрещает Tilda↔Telegram (персональные данные посетителей), а не Django↔Supabase (только
  контент новостей, без PII). Уточнить у Бро на всякий случай перед стартом, но по букве
  решения это другой периметр.

## Задача 1 (этот проект, `Парсер новостей ГЛ`): отправка в ЛК при публикации

Место — `news/publishing/`, туда же, где уже есть `TelegramPublisher`
(`news/publishing/telegram.py`) и `publish_from_queue` (`news/publishing/tasks.py`).

**Архитектурная рекомендация: использовать существующую модель `PublishChannel`, а не отдельный
путь кода.** `PublishChannel.ChannelType` сейчас — `telegram`/`lk_webhook`/`lk_api` (см.
`news/models.py`) — `lk_api` уже зарезервирован под этот случай, просто не реализован.
`publish_from_queue` уже итерирует по активным каналам на каждую статью — добавление ветки
`elif channel.channel_type == PublishChannel.ChannelType.LK_API` в этот же цикл переиспользует
готовую инфраструктуру retry/`PublicationLog`/аудита, а не создаёт параллельную.

Шаги:

1. **Новые настройки** (`config/settings.py` + `.env.example`): `LK_PUBLISH_NEWS_URL`
   (полный URL Edge Function, вида `https://<project-ref>.supabase.co/functions/v1/publish-news`),
   `LK_NEWS_TOKEN` (то же значение, что задано в Supabase secrets на стороне ЛК — согласовать
   с Бро/кодером ЛК, это общий секрет двух систем).
2. **Новый клиент** `news/publishing/lk.py` (по аналогии с `telegram.py`) — функция
   `push_to_lk(article) -> None`, делает `POST` на `LK_PUBLISH_NEWS_URL` с
   `Authorization: Bearer <LK_NEWS_TOKEN>` и телом:
   ```json
   {
     "title": "...",
     "body": "...",
     "is_urgent": true,
     "category": "resort_cis",
     "source_name": "Роза Хутор",
     "source_url": "https://rosakhutor.ru/news/..."
   }
   ```
3. **Формат `title`/`body` — НЕ то же самое, что уходит в Telegram.** Для Telegram
   (`_format_for_telegram`, `news/publishing/tasks.py`) заголовок оборачивается в `<b>`, тело
   содержит хэштеги и заменяет ссылку на голое имя источника (антиспам-требование канала —
   это специфика Telegram, к ЛК не относится). Для ЛК нужна отдельная, более простая
   сборка:
   - `title` = `article.edited_title` как есть.
   - `body` = `article.edited_post_text` **без** заголовка (первая строка), **без** хэштегов
     (последняя строка, если начинается с `#`), **без** строки «Источник: ...» (она уходит
     отдельными полями `source_name`/`source_url`), без markdown-звёздочек. Реализация может
     переиспользовать `SOURCE_LINE_RE` из `news/editor/pipeline.py` для отделения строки
     источника, но саму сборку текста для ЛК писать отдельной функцией — не подмешивать в
     `_format_for_telegram`, у форматов разные потребители и разные правила (это НЕ дублирование
     ради дублирования, а отражение того, что Telegram и веб-карточка ЛК — разные площадки со
     своими ограничениями).
   - `source_url` = `article.external_url`, `source_name` = `article.source.name`.
4. **Категория.** У `Article`/`Source` сейчас нет поля, соответствующего enum'у ЛК
   (`club|world_cup|resort_cis|resort_asia|resort_europe|resort_americas`). Добавить новое
   поле `Source.lk_category` (`CharField` с `choices`, значение по умолчанию — решить при
   реализации, разумный дефолт `resort_cis`, т.к. большинство подключённых источников — это
   курорты РФ/СНГ), редактируемое в Django admin. Заполнить для всех текущих 16 источников при
   миграции — ориентировочно: `world_cup` — Superski.ru, Ski Racing Media; `resort_cis` —
   все остальные (курорты РФ + Каракол, Киргизия — формально СНГ). Финальную раскладку по
   источникам, где неочевидно (например, нужен ли вообще `resort_asia`/`resort_europe`/
   `resort_americas` при текущем составе источников, или это категории на будущее) —
   уточнить у Бро, не решать самостоятельно втихую при реализации.
5. **Вызов** — в `publish_from_queue` (`news/publishing/tasks.py`), в существующем цикле по
   `channels`, добавить обработку `PublishChannel.ChannelType.LK_API`: вызвать `push_to_lk`,
   обернуть в `try/except`, записать результат в `PublicationLog` (как уже делается для
   Telegram) — ошибка отправки в ЛК не должна блокировать/откатывать успешную публикацию в
   Telegram и наоборот, это независимые каналы (тот же принцип, что уже реализован для
   fallback `sendPhoto → sendMessage`).
6. **Создать `PublishChannel`** (`channel_type='lk_api'`, `is_active=True`) через Django
   admin — как уже сделано для Telegram-канала (`config` пока может быть пустым `{}`, URL/токен
   берутся из settings, не из `config`, в отличие от Telegram, где `chat_id` в `config`
   — обсудить при реализации, нужна ли вообще вариативность на будущее для нескольких ЛК/сред).

## Проверка готовности

- Тестовая новость, отправленная из `publish_from_queue` (например, вручную через
  `python manage.py shell` на реальной/тестовой статье), реально появляется в таблице `news`
  Supabase со всеми полями (включая `category`/`source_name`/`source_url`).
- Ошибка сети/токена при отправке в ЛК не мешает той же новости уйти в Telegram (и наоборот).
- `PublicationLog` содержит запись о попытке отправки в ЛК, успешной или нет.
- `/lk` на реальном опубликованном сайте показывает реальную последнюю новость вместо
  заглушки «в разработке», без ошибок в консоли, без XSS-уязвимости при заголовке/тексте,
  содержащем HTML-подобные символы (`<`, `>`, `&`) — тестовый кейс, не полагаться на то, что
  источники «обычно безопасны».
