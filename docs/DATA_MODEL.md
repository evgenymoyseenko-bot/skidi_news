Ниже — спецификация моделей, а не готовый код. Разработчик реализует `models.py` по этому
описанию; конкретные Django-идиомы (related_name, indexes, Meta) — на усмотрение кодера, если

**Уточнение от 04.09.2026**: раздел `Article` ниже расширен под связку Парсер → LLM-Редактор →
Модератор (по email) → Очередь публикации — это отдельная ветка разработки (`parser/` в папке

## Модерация по email и очередь публикации (уточнено 04.09.2026)

Эта связка — прослойка между LLM-редактором и Django-моделью `Article` выше, отдельная ветка
разработки (`parser/`). Ниже — согласованная с пользователем спецификация; в паре мест явно
помечено, что решение моё предложение (пользователь прямо попросил предложить механизм), а не
его прямое указание — стоит проверить при кодировании.

### 1. От редактора — к очереди на модерацию

LLM-редактор (см. `parser/EDITOR_PROMPT.md`) обрабатывает батч и для каждой новости выставляет
`editor_verdict`. Для `publish`: заполняются `edited_title`, `edited_post_text`,
`editor_processed_at`, `status` → `pending_moderation`. Для `reject` — новость дальше не идёт
(отдельного статуса не нужно, реализуется на уровне «редактор её просто не вернул в списке
одобренных», либо `status` остаётся как было — деталь на усмотрение кодера).

Квота редактора — **6 новостей в день** (подтверждено пользователем), делится **по 3 на
батч** (06:00 и 18:00 UTC) — решение кодера, зафиксировано 07.09.2026. Если редактор в рамках
одного прогона одобрил больше 3 — берутся первые 3 по `source_published_at` (старые вперёд),
остальные остаются необработанными (`editor_processed_at` не проставляется) и попадают в
следующий прогон вместе с новым батчем.

### 2. Письмо модератору

- Один email на одну новость, на `info@skidiscoverer.ru` — не батчем, отправляется сразу после
  того, как редактор обработал конкретную запись (`pending_moderation` + email ещё не отправлен),
  чтобы модератор мог реагировать по мере поступления, а не ждать конца батча.
- Тело письма: `edited_title`, `edited_post_text` целиком (уже включает ссылку на источник —
  обязательное требование пользователя: «Новость должна ссылаться на источник публикации откуда
  она взята»), картинка (`image_url`), и три ссылки-действия:
  - **«Опубликовать»** → одобрить, обычный приоритет.
  - **«Опубликовать срочно»** → одобрить + `is_urgent=True`.
  - **«Отклонить»** → отклонить.
- После отправки — `moderation_email_sent_at = now()`, чтобы задача-рассыльщик не отправила то
  же письмо повторно при следующем прогоне.

### 3. Механизм ссылок — моё предложение («как это сделать предложи»)

- Ссылка = URL Django-view с подписанным токеном:
  `django.core.signing.dumps({"article_id": ..., "action": "publish" | "publish_urgent" | "reject"})`
  через `TimestampSigner`, с разумным `max_age` (например, 30 дней — с запасом, модератор может
  открыть письмо не сразу). Источник: [Django docs — Cryptographic
  signing](https://docs.djangoproject.com/en/5.2/topics/signing/) — стоит свериться с актуальной
  версией доки перед реализацией, я не проверял код руками.
- Отдельная таблица токенов не нужна — подпись сама себя валидирует. Защита от повторного
  использования (реплей, случайный второй клик, пересланное письмо) — не через одноразовость
  токена, а через проверку текущего `status` статьи в момент перехода по ссылке: если уже не
  `pending_moderation` — view показывает «уже обработано», ничего повторно не меняет.
- Клик не требует логина в Django — сама подпись и есть авторизация, а ящик `info@` закрытый.
  Это осознанный компромисс: если в будущем к ящику будет доступ у нескольких человек и понадобится
  знать, кто именно кликнул — можно добавить промежуточную страницу подтверждения с выбором
  пользователя. Сейчас это не запрошено.
- GET-запрос, меняющий состояние по клику из письма — сознательное отступление от обычного правила
  «GET не должен менять состояние», ради UX одного клика; так же устроены типовые
  email-unsubscribe-ссылки, считаю компромисс приемлемым для этого случая.
- **Не тестировано** — это предложенный дизайн, а не проверенный код, проверить перед
  использованием.

### 4. Очередь публикации

Не отдельная таблица — вычисляемая выборка:

```python
Article.objects.filter(status='approved').order_by('-is_urgent', 'source_published_at')
```

Срочные (`is_urgent=True`) — всегда первыми (между собой — по дате источника), остальные — по
`source_published_at` от старой к новой, как явно попросил пользователь («ставятся в очередь
согласно дате публикации источника»).

**Без лимита записей и без вытеснения (уточнено 04.09.2026, ревизия 2 — отменяет более раннюю
идею с лимитом в 8 записей и статусом `expired_unpublished`).** Пользователь явно отказался от
удаления/вытеснения: «не удаляем стэк». Вместо лимита — очередь публикации ничем не ограничена и
естественно растёт, если предложение превышает дневной спрос (4 новости/день). Проблему
устаревания старых неопубликованных новостей решает не лимит, а еженедельная повторная
модерация (п. 6 ниже) — раз в неделю все зависшие в очереди записи уходят обратно модератору на
подтверждение, чтобы совсем старые новости не публиковались без свежей проверки.

### 5. Публикация по расписанию

Подтверждено (уточняющий вопрос, 04.09.2026): **2 новости на каждый из двух батч-таймов = 4 новости
в день суммарно** (06:00 и 18:00 UTC, синхронно с расписанием парсера).

Каждый прогон публикующей Celery-таски берёт первые 2 записи из очереди (п. 4) — `is_urgent` первыми,
дальше по `source_published_at` от старой к новой — публикует их (через активные `PublishChannel`,
обычно Telegram), переводит `status` → `published`, `published_at = now()`.

Если одобренных-неопубликованных записей в очереди больше, чем нужно на сегодня (больше 4) —
лишние просто остаются в очереди до следующего дня, никакого специального механизма не требуется
(это и есть «естественный рост очереди» из п. 4). Если запись сегодня взята в паре 2 руками
таски, а очередь на следующий день выбирает заново — это обычная работа `order_by`, отдельно
ничего резервировать не нужно.

**Если новостей в очереди меньше 4** (то есть на сегодняшний день не хватает одобренного
материала на обе публикации) — уходит письмо-напоминание модератору на `info@skidiscoverer.ru`
о том, что стэк неполный и он может опубликовать что-то своё в Telegram-канал вручную, если
хочет. Моё предложение по месту проверки: делать эту проверку один раз в день, на первом
(06:00 UTC) прогоне публикующей таски — иначе при коротком прогоне в 18:00 UTC можно было бы
дважды напомнить об одном и том же дефиците за день; это деталь реализации, не описанная
пользователем явно, стоит проверить перед кодированием.

### 6. Еженедельная повторная модерация (новое, 04.09.2026, ревизия 2)

Пользователь: «все неопубликованные новости нужно раз в неделю присылать на повторную
модерацию, чтобы не было публикаций слишком старых новостей» — это и есть механизм борьбы со
старением очереди вместо лимита/вытеснения из п. 4.

- **Расписание** (подтверждено уточняющим вопросом): **понедельник, 06:00 UTC** — совпадает по
  времени с обычным утренним батчем парсера, отдельного нового времени в расписание не
  добавляется.
- **Отбор**: все записи `status='approved'` с `published_at IS NULL` (то есть весь текущий
  «зависший» остаток очереди публикации на момент запуска).
- **Формат** (подтверждено уточняющим вопросом): **одно письмо-дайджест**, а не пачка отдельных
  писем — список всех отобранных новостей (`edited_title` + короткий текст/ссылка на источник),
  и у каждой строки — те же три ссылки-действия, что и в обычном письме модерации (п. 2–3):
  «Опубликовать» / «Опубликовать срочно» / «Отклонить». Механизм ссылок — тот же подписанный
  токен (`django.core.signing`, п. 3), просто применяется повторно к записи, которая уже
  `approved` (а не только к `pending_moderation`); проверка при переходе по ссылке та же —
  смотрим текущий `status`/`published_at`, чтобы клик по устаревшей ссылке из старого дайджеста
  не наделал лишнего, если запись уже опубликована или отклонена к этому моменту.
- **После рассылки дайджеста** — `last_requeue_email_sent_at = now()` на каждой включённой
  записи (для аудита, не для защиты от повтора — задача и так разовая, раз в неделю).
- Само решение модератора (клик по ссылке) не меняет `status` автоматически на что-то новое —
  использует тот же путь, что и обычная модерация: «Опубликовать»/«Опубликовать срочно» оставляют
  `status='approved'` (при необходимости выставляя `is_urgent`), «Отклонить» переводит в
  `rejected`. Если модератор дайджест проигнорировал — запись просто остаётся в очереди до
  следующего понедельника, это ожидаемое поведение, не ошибка.

### 7. Разночтение «стэк» — предложение по терминологии

В переписке словом «стэк» названы два разных понятия — стоит развести в коде и документации:

- **«Дневная квота редактора»** (6/день) — сколько новостей редактор в принципе отправляет на
  модерацию за день. Не отдельное поле БД, это ограничение уровня промпта/логики редактора.
- **«Очередь публикации» (publication queue)** — вычисляемая выборка `Article(status='approved')`,
  без верхнего лимита (п. 4). Именно её пользователь описывал как «стэк для публикации».
  Предлагаю в коде и документации закрепить только термин «очередь публикации» /
  `publication queue`, оставив «стэк» бытовым словом только для чата.

| attempt_number | PositiveSmallIntegerField, default=1 | Для ретраев |

Нужен для аудита («новость точно ушла в Telegram?») и для повторных попыток при сетевых сбоях
(Celery retry с backoff).

## Django Admin — настройка

### `ArticleAdmin`

**Уточнение 07.09.2026 (исправляет расхождение с `docs/CODER_INSTRUCTIONS.md`, Этап 1):** ниже
описанные admin-actions «Одобрить и опубликовать» / «Отклонить» **больше не реализуются** —
это версия раздела до перехода на email-модерацию по подписанным ссылкам (см. «Модерация по
email и очередь публикации» выше в этом файле). `ArticleAdmin` — только для видимости и
отладки, окончательное решение о публикации принимается по клику в письме, не в admin.

- `list_display`: превью заголовка, источник, категория, статус, `is_urgent`, дата источника,
  миниатюра картинки.
- `list_filter`: `status`, `category`, `source`.
- `search_fields`: `title`, `summary`.
- Никаких admin-actions для одобрения/отклонения — модерация только через email-ссылки.
- Поле `edited_post_text` — редактируемое (модератор может вручную поправить текст до того, как
  письмо уйдёт, если правит запись раньше рассылки), но это не основной канал принятия решений.

### `SourceAdmin`

- Обычный CRUD.
- Admin action **«Запустить парсинг сейчас»** — ручной триггер Celery-таски парсинга конкретного
  источника (полезно для проверки нового источника, не дожидаясь расписания).
- `readonly_fields`: `last_parsed_at`, `last_parse_status`, `last_parse_error`.

### Расписание парсинга

Периодические задачи настраиваются не в коде, а в стандартной админке `django-celery-beat`
(модели `PeriodicTask`/`IntervalSchedule`, которые эта библиотека сама регистрирует в admin).
Рекомендуемая практика: одна периодическая задача `run_all_active_sources`, которая сама внутри
проверяет `parse_interval_minutes` каждого `Source` и решает, кого пора опрашивать (проще
поддерживать, чем создавать отдельную периодическую задачу на каждый источник).
