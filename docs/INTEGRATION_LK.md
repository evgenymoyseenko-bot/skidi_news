Этот документ описывает интеграцию по модулю `news`. Симметричный pull-контракт для базы
знаний (`GET /api/v1/knowledge-base/...`) — в `docs/KNOWLEDGE_BASE.md`; приём заявок на
консультацию от ЛК (если ЛК тоже захочет свою форму, не только Тильда) — `POST
/api/v1/consultations/` в `docs/CONSULTATIONS.md`. Аутентификация везде единая — один
`LK_API_TOKEN` на весь бэкенд, а не отдельный секрет на каждый раздел.

ЛК — отдельный проект в разработке (лендинг на Тильде + отдельный Личный кабинет с
информационной базой), стек ещё не зафиксирован. Поэтому контракт ниже сознательно
универсален (обычный REST/JSON поверх HTTPS) и не завязан на конкретный фреймворк ЛК.

## Модель интеграции: pull + опциональный push

**Базовый вариант — pull (ЛК сам запрашивает новости).** Это самый развязанный вариант: парсер
ничего не должен знать про ЛК заранее, а ЛК подключается тогда, когда будет готов.

**Опциональное расширение — push (вебхук).** Когда стек ЛК определится и понадобится
показывать новости «в реальном времени» без опроса, добавляем исходящий вебхук — парсер сам
уведомляет ЛК при публикации. Это дополнение к API, а не замена: pull-эндпоинт остаётся
источником истины (на случай, если вебхук не дошёл — ЛК может досверить данные через GET).

## Аутентификация

Сервер-сервер, без пользовательского контекста → простой статический ключ в заголовке, без
OAuth-костылей:

```
Authorization: Bearer <LK_API_TOKEN>
```

Токен — общий секрет, задаётся в `.env` обеих сторон (`LK_API_TOKEN` у парсера,
соответствующее значение — у ЛК). Ротация — вручную при необходимости на старте проекта
достаточно.

## Pull: REST API (эндпоинты парсера, которые вызывает ЛК)

### `GET /api/v1/news/`

Список опубликованных новостей.

Query-параметры:

| Параметр | Тип | Описание |
|---|---|---|
| `category` | slug | Фильтр по категории |
| `since` | ISO datetime | Только новости, опубликованные после этой даты (для инкрементальной подгрузки) |
| `page`, `page_size` | int | Пагинация (DRF PageNumberPagination) |

Пример ответа:

```json
{
  "count": 42,
  "next": "https://.../api/v1/news/?page=2",
  "previous": null,
  "results": [
    {
      "id": 123,
      "title": "...",
      "summary": "...",
      "content": "...",
      "image_url": "https://...",
      "category": "nauka",
      "source_name": "...",
      "source_url": "https://...",
      "published_at": "2026-08-20T10:00:00Z"
    }
  ]
}
```

Отдаются только `Article.status == published`. Внутренние поля модерации (`moderated_by`,
`moderation_comment`, `raw_payload` и т.п.) в ответ не попадают.

### `GET /api/v1/news/{id}/`

Одна новость, тот же набор полей.

### `GET /api/v1/categories/`

Список категорий (`slug`, `name`) — чтобы ЛК мог строить фильтр без хардкода рубрик.

## Push: исходящий вебхук (опционально, включается позже)

При переводе `Article.status → published` парсер, если задан `LK_WEBHOOK_URL`, отправляет:

```
POST <LK_WEBHOOK_URL>
Authorization: Bearer <LK_API_TOKEN>
Content-Type: application/json

{
  "event": "news.published",
  "article": { ...тот же формат, что и в GET /api/v1/news/{id}/... }
}
```

Требования к отправке:

- Retry с экспоненциальной задержкой при ошибке/таймауте (Celery `autoretry_for`,
  например 3 попытки: сразу, через 1 мин, через 5 мин).
- Каждая попытка логируется в `PublicationLog` (см. `DATA_MODEL.md`) — если все попытки
  провалились, новость всё равно доступна через pull-API, потеря данных исключена.
- ЛК обязан отвечать `2xx` быстро (принял в очередь) и не блокировать вебхук долгой
  обработкой — это стандартная практика для вебхуков, снижает риск ложных ретраев.

## Идемпотентность на стороне ЛК

`Article.id` (или `external_url`) — стабильный идентификатор. При повторном pull или повторном
вебхуке (например, после ретрая) ЛК должен делать upsert по этому id, а не создавать дубликаты.

## Что не входит в ответственность парсера

- Разграничение доступа к новостям по тарифу подписки — это логика ЛК. Если понадобится
  сегментация, на стороне парсера потребуется добавить поле `visibility`/`tier` в `Article`
  и прокидывать его в ответ API — сейчас не делаем, чтобы не проектировать вслепую то, что
  зависит от ещё не спроектированной модели подписок в ЛК.
- Хранение прочитанных/непрочитанных статусов на пользователя — это тоже сторона ЛК.

## Открытый вопрос

Как только стек ЛК будет выбран, стоит явно согласовать: (1) итоговый `LK_WEBHOOK_URL` и его
доступность (публичный ли у ЛК backend адрес на этапе разработки), (2) нужен ли push вообще
на старте, или pull с коротким интервалом опроса (например, раз в 5 минут) полностью закроет
потребность для MVP.
