# Парсер новостей — минимальный скелет (часть 1: Парсер, без Редактора)

Реализация первого шага из архитектурного обсуждения: один источник, без дедупликации,
без Django/Celery. Схема данных и решение по дедупу — см. переписку по архитектуре парсера
(этот код реализует вариант со схемой из раздела 1 и заглушкой вместо реального дедупа).

## Что здесь есть

- `schema.py` — `NewsItem`: схема одной новости, которая должна уходить дальше (редактору).
- `sources.py` — конфиг источника (`SourceConfig`) и `fetch_source()`: тянет RSS, приводит
  каждую запись к `NewsItem`. Один тестовый источник — RSS ТАСС (`tass.ru/rss/v2.xml`,
  общая лента крупного СМИ, RSS проверен вручную; заменён с `rider-skill.ru` 04.09.2026 по
  запросу пользователя — подробности замены см. ниже и в докстринге `sources.py`).
- `main.py` — точка входа: собирает батч по всем источникам (сейчас — один), печатает и
  сохраняет в `batch_output.json`. Передача батча редактору — **заглушка**, реального
  транспорта пока нет (это открытый вопрос, см. архитектурное обсуждение).
- `tests/` — тесты на зафиксированной копии настоящего RSS-ответа (не на выдуманном XML).

## Правила фильтрации на стороне парсера (уточнено 03.09.2026, картинка — 07.09.2026)

Помимо схемы данных, парсер теперь сам отбраковывает часть записей — но только по
**детерминированным** признакам, не по субъективной оценке "хорошая ли новость":

- **Картинка необязательна (уточнено 07.09.2026, отменяет более раннее решение).** До
  07.09.2026 картинка была обязательным полем, и записи без неё отбрасывались целиком. По
  прямому запросу пользователя это правило отменено: `image_url` в схеме снова `Optional`
  (см. `schema.py`). Если картинка нашлась (в `media:content`, `content:encoded` или
  `summary`) — публикуем с ней, если нет — `image_url=None`, запись всё равно идёт в батч.
- **Категория "обучение" исключается.** Если у записи RSS есть тег `<category>`,
  содержащий подстроку "обучен" (ловит "Обучение", "Советы по обучению" и родственные
  варианты) — запись отбрасывается в `fetch_source`, независимо от наличия картинки.
  Список подстрок — `EXCLUDED_CATEGORY_SUBSTRINGS` в `sources.py`, специально сделан
  расширяемым множеством, а не захардкожен в логике.

- **Не старше 30 дней.** Новая константа `MAX_ARTICLE_AGE_DAYS = 30` в `sources.py`. Запись
  без распознанной даты публикации тоже считается "слишком старой" и отбрасывается — осознанный
  дефолт (нельзя подтвердить свежесть без даты), см. докстринг `_is_too_old`, легко поменять на
  противоположный одной строкой.

Все три правила — про детерминированные признаки (наличие поля, точный тег, сравнение дат), а
не про смысловую оценку контента, поэтому они законно живут в парсере, а не нарушают разделение
"парсер не судит о качестве, это работа редактора".

**Находка при добавлении правила "не старше 30 дней" (03.09.2026, история):** прежний тестовый
источник `rider-skill.ru/feed/` публиковал нечасто — самая свежая запись в его RSS на момент
проверки была почти двухмесячной давности, из-за чего с правилом 30 дней все записи фикстуры
отбрасывались по возрасту. Источник заменён на ТАСС именно поэтому в том числе (публикует
намного чаще). Практический вывод остаётся актуальным для выбора финального списка источников
(см. `docs/SOURCES.md`): смотреть не только на тематику, но и на частоту публикаций — источник,
который постит раз в 1-2 месяца, с правилом "30 дней" почти всегда будет давать пустой результат.
Тест на фикстуре (`FeedToNewsItemTests`) на всякий случай всё равно отключает правило возраста
для себя (чтобы не протухнуть самому со временем) — само правило отдельно проверено на
синтетических данных в `TooOldRuleTests`.

**Замена тестового источника (04.09.2026):** по прямому запросу пользователя ("убери
rider-skill.ru из теста, выбери что-то из крупных СМИ") источник заменён на общую RSS-ленту
ТАСС. Побочная находка при подборе: у **РИА Новости** (тоже крупное СМИ, был первым кандидатом)
публичная RSS-лента вообще не содержит текста записей — только заголовок, ссылка и картинка,
без `<description>`/`<content:encoded>`. Это реальное архитектурное ограничение источника, а не
баг: если РИА Новости в итоге войдёт в финальный список источников, для него понадобится
полноценное извлечение текста со страницы статьи (trafilatura, уже выбран в проекте), RSS-текста
одного будет недостаточно. У ТАСС `<description>` в записях есть — выбран поэтому. Ни у ТАСС, ни
у РИА нет отдельной рубрики/RSS именно под "горные лыжи" — обе ленты общие. Зафиксированная
фикстура (`tests/fixtures/tass_sample.xml`) — вручную отобранные 12 нейтральных по теме записей
(спорт/экономика/культура/наука) из живой ленты, а не "как есть" — полная лента на момент отбора
содержала много новостей о военном конфликте и происшествиях, что не годится для тестового
файла в этом репозитории ни тематически, ни по чувствительности содержимого.

**Реклама намеренно не фильтруется здесь.** Историческая находка (03.09.2026, на прежней
фикстуре rider-skill.ru, которая больше не используется в тестах — см. выше): встретилась
запись «Лучшие инструкторы по горным лыжам и сноуборду на Газпром Поляне: открыто бронирование
на сезон 2026/2027», по факту рекламный пост о бронировании услуг, оформленный как новость. В
том конкретном случае она всё равно отсеялась другими правилами (без картинки + тег "Обучение"),
но это было совпадение, а не результат работы отдельного анти-рекламного фильтра — следующая
такая запись может иметь и картинку, и не быть тегирована "обучением". Ловить рекламу
эвристиками в парсере ненадёжно (нет чёткого детерминированного признака) — по архитектуре это
явно зона ответственности LLM-редактора (часть 2, промт уже есть — см. `EDITOR_PROMPT.md`).
Держим этот пример как заготовку для промта: "рекламные посты, замаскированные под новость
(например, анонс бронирования услуг конкретной школы/инструкторов) — не публиковать" (в
текущем промте это уже покрыто пунктом "рекламные материалы, замаскированные под новости").

## Что реально проверено, а что нет

**Проверено** (реальными данными, не только "выглядит логично"):
- Маппинг RSS-записи → `NewsItem`, очистка HTML из title/text, разбор даты, извлечение
  картинки (через `<enclosure type="image/...">`, стандарт ТАСС), стабильность и уникальность
  `internal_id` — всё прогнано на зафиксированной копии реальных данных ТАСС
  (`tests/fixtures/tass_sample.xml`, отобрано 04.09.2026 из живой ленты `tass.ru/rss/v2.xml`).
- Правило "картинка необязательна" (что и с картинкой, и без неё запись остаётся в батче, с
  корректным `image_url`/`None`) проверено и на этой фикстуре, и отдельно на синтетических
  RSS-фрагментах. Правила "категория обучение" и "не старше 30 дней" эта фикстура не содержит
  (у ТАСС нет такой категории) — проверены независимо синтетическими фрагментами.
- 20 тестов, все проходят (`python3 -m unittest discover -s tests -v`).
- Ранее (на прежнем источнике rider-skill.ru) в процессе тестирования нашёлся и исправлен
  реальный баг: картинки в WordPress-фидах могут лежать не в `summary`, а в `content:encoded` —
  код в `_extract_image()` по-прежнему проверяет оба места, на случай если такой источник
  появится в финальном списке.

**НЕ проверено** (важно понимать перед использованием):
- Живой HTTP-запрос к источнику — среда, где это писалось, не имеет сетевого доступа к
  произвольным сайтам (только к пакетным реестрам). `fetch_source()` технически идентичен
  тому, что прогонялось на фикстуре (`feedparser.parse()` одинаково принимает и URL, и путь
  к файлу), но сам факт "сайт ответит и не отдаст 403/капчу боту" — не проверен. Перед
  реальным использованием стоит один раз прогнать `python3 main.py` в среде с обычным
  доступом в интернет и убедиться, что `batch_output.json` не пустой.
- Поведение на других источниках (не ТАСС) — извлечение картинки и текста проверялось на
  двух реальных фидах за всё время (rider-skill.ru через `content:encoded`, ТАСС через
  `<enclosure>`), но не на всех форматах сразу. Другой источник может отдавать RSS иначе.

## Как запустить

```bash
pip install -r requirements.txt
python3 -m unittest discover -s tests -v   # тесты на зафиксированных данных
python3 main.py                             # реальный запрос к источнику + сохранение батча
```

## Сознательно не сделано на этом шаге (следующие итерации)

- Дедупликация (ни точная по URL, ни нечёткая по заголовку) — `canonicalize_url()` уже есть
  и используется для `internal_id`, но проверки "уже видели ли мы этот URL" нет.
- Несколько источников одновременно (структура уже под это готова — `SOURCES` — список).
- Реальный триггер батча — архитектура подтверждена пользователем (03.09.2026): **батч по
  расписанию**, 2 раза в день, 06:00 UTC и 18:00 UTC (то есть это вариант A из исходного
  архитектурного предложения — не поток и не гибрид-микробатч). Технически — Celery beat /
  cron с двумя фиксированными временами. Сейчас в коде это не реализовано, скрипт всё ещё
  запускается вручную.
- Передача батча редактору — сейчас просто JSON-файл на диске.
- Интеграция с Django/Celery/Postgres, если это в итоге окажется частью общего проекта
  skidiscoverer, а не отдельный сервис (открытый вопрос архитектуры).
